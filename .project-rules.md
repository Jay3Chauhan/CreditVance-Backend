# Enterprise Engineering & Project Rules

This document establishes the engineering standards, architecture constraints, and coding rules for the **Credit Card Smart Advisor & Vault Backend**.

---

## 1. Core Architecture Principles

1. **Domain-Driven Design (DDD) & Clean Architecture**:
   - **`app/models`**: Pure SQLAlchemy 2.0 ORM entities. Never mix business logic in models.
   - **`app/schemas`**: Strict Pydantic v2 DTOs for request/response serialization and validation.
   - **`app/services`**: Encapsulates 100% of business logic, third-party ingestion, recommendation math, and database transactions.
   - **`app/api/v1`**: Thin transport controllers. They parse requests, call services, and return standardized responses.
   - **`app/core`**: Infrastructure configuration, database engine, Redis client, logging, and security.

2. **Zero Third-Party Runtime Passthrough**:
   - The mobile client (Flutter) or web client must **NEVER** call third-party APIs (SaveSage Club) directly.
   - All client queries are served from **Neon PostgreSQL** and **Upstash Redis**.
   - SaveSage APIs are contacted exclusively by the asynchronous crawler (`CrawlerService` / `SyncService`) via scheduled cron jobs or authenticated admin triggers.

3. **PCI-DSS Compliance & Zero-Knowledge Security**:
   - Full 16-digit Primary Account Numbers (PANs), CVVs, and plain magnetic stripe/chip data must **NEVER** be stored in the cloud database.
   - Card numbers are held strictly on the user's physical mobile device using hardware-backed secure storage (iOS Keychain / Android Keystore with Biometrics).
   - The backend database only stores non-sensitive card metadata: `card_id`, `nickname`, `last_4_digits`, `card_network`.

4. **100% Free Tier Optimization**:
   - **Neon PostgreSQL**: Operate with pooled connection strings (`PgBouncer`). Keep connection count low using async sessions (`asyncpg`).
   - **Upstash Redis**: Cache catalog and calculator taxonomies with 1h - 24h TTLs to respect the 10,000 commands/day free tier quota.
   - **Oracle Cloud Free VM**: Keep memory footprint under 512MB for the Python container using async IO and minimal idle threads.

## 2. Python & Code Quality Standards

1. **Python 3.12+ Modern Features**:
   - Use built-in generics (`list[str]`, `dict[str, Any]`, `X | None` instead of `typing.Optional` / `typing.Union`).
   - Use strict type annotations across all function signatures and return types.
2. **Async Everywhere**:
   - All I/O operations (database queries, Redis calls, HTTP crawling) must use `async/await`.
   - Never use blocking synchronous libraries inside async endpoints (use `httpx.AsyncClient` not `requests`, `asyncpg` not `psycopg2`).
3. **Structured Logging**:
   - Use `loguru` with structured contextual tags (`card_slug`, `user_id`, `sync_id`).
   - Never use `print()` statements in production code.
4. **Standard API Response Envelope**:
   - Every API response must conform to `ApiResponse[T]`:
     ```json
     {
       "success": true,
       "message": "Operation successful",
       "data": { ... },
       "meta": null,
       "error": null
     }
     ```
   - Standard error envelope:
     ```json
     {
       "success": false,
       "message": "Error description",
       "data": null,
       "error": {
         "code": "CARD_NOT_FOUND",
         "details": "Card with slug 'invalid-card' does not exist."
       }
     }
     ```

## 3. Database & Migration Rules

1. **SQLAlchemy 2.0 Style**:
   - Use `select()`, `insert()`, `update()` statements with `await db.execute()` and `scalars().all()`.
   - Avoid legacy 1.4 query methods (`db.query()`).
2. **Alembic Migrations**:
   - Every schema change must be accompanied by an Alembic migration script.
   - Never use `Base.metadata.create_all()` in production code.
3. **Indexes**:
   - Always index foreign keys and high-frequency search fields (`slug`, `bank_id`, `network_type`, `is_popular`).
   - Tab details and complex perk definitions are stored in `JSONB` for schema flexibility and fast reading.

---

## 4. Crawling & Sync Guidelines

1. **Polite Crawling & Rate Limiting**:
   - Minimum 150ms-250ms delay between consecutive requests to external APIs.
   - Maximum concurrency of 5 async workers to prevent rate limiting (HTTP 429).
   - Use exponential backoff with jitter on 429 or 5xx responses.
2. **Distributed Locking**:
   - Always acquire `lock:sync:savesage` in Redis before starting a sync job to prevent duplicate cron executions.
3. **Resumable & Idempotent**:
   - Card records are upserted (`ON CONFLICT (slug) DO UPDATE`).
   - Sync progress is logged to the `sync_audit_logs` table for observability.
